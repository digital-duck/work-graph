work-graph

A personal AI assistant built on a knowledge-base graph for SDLC


wen.gong.research@gmail.com

https://github.com/digital-duck/work-graphHackathon project, early prototype
workgraph is a hackathon project and an early prototype. It treats everything you produce and consume while building software as nodes in one graph. The assistant then reasons over that graph instead of over a single file or chat window.

Outline

    The outline lists every slide title; click a line to jump.

    Assistants see only a snapshot

    • Most AI coding assistants see the open file, a few neighbours and a chat history.
    • The things that make software work sit outside that window.
    • That knowledge is scattered across repos, docs, tickets, notes, machines and your head.
    • It is relational, so a graph is a natural way to store it.

    Questions the window cannot answer

    Why was this designed this way?
    Which requirement does this function satisfy, and which tests cover it?
    Which paper, ticket or Slack thread explains this workaround?
    What did I learn last time I hit this class of bug?
    The decision made three months ago, the requirement and the tests are not in the open file. Each new session starts cold. workgraph keeps this knowledge in one graph.

    One graph, many artifact types

    • Requirements, design decisions, code, tests, bugs, meetings, papers and half-formed ideas become linked nodes.
    • The graph models the lifecycle, so traceability comes from the links: requirement → design → implementation → test → release.
    • Personal first: it runs locally, you own it, and it persists in plain files.
    • Answers are grounded in a subgraph (a node, its neighbourhood, the paths between nodes), not only in top-k text chunks.
    • Answers can cite the nodes they used.
    Code is one kind of knowledge among many. The same engine also covers reading notes, research, meeting outcomes and retrospectives.

    Graph artifacts drive the AI workflow

    • Persistent context: a file that outlives any one conversation and that any tool can read.
    • Before a task, an agent loads the relevant sub-graph instead of finding everything again in raw files.
    • The graph steers the work: gap rules, process stages and open work items show the next step.
    • Agent output is written back into the graph.

    Human in the loop

    ✔ LLM-proposed nodes and edges are INFERRED
    ✔ they stay that way until a person confirms them in the YAML review format
    ✔ agents and people read and write the same artifacts
    The graph files are the working memory of the AI-assisted process, not a report generated at the end. Any agent can use them, whether it is Claude Code, another assistant or a script. Nothing depends on one tool's private memory.

    A thin layer over graphify

    • The engine is graphify, used as a library from PyPI (graphifyy[sql]>=0.7.19).
    • graphify provides file detection, tree-sitter extraction for about 25 languages, LLM extraction, entity dedup, Leiden clustering, queries and export.
    • The graph is a NetworkX graph throughout.
    • workgraph adapts it to an area by supplying an area pack.

    Other dependencies

    dd-llm every LLM call
    graflang the recipes
    zinet graph drawing
    dd-embed semantic search
    workgraph does not reimplement extraction or clustering. It adds the lifecycle vocabulary, the links and the gap rules on top of graphify.

    Area packs: vocabulary and processing

    • Vocabulary: stages and their flow, legal relations, gap rules, path classifiers.
    • Processing: which file type goes through which processor and LLM backend, e.g. *.py → tree-sitter, *.md → frontmatter.
    • A new area is a new YAML file. Each project in a workspace picks its own pack.
    • New: the design pack for products that mix hardware and software. Its design step is an architecture graph (*.arch.yaml), and a part list counts as a build artifact.
    $ workgraph utils areas
sdlc        Software development lifecycle: requirement → design
            → build → test → release → operate
research    Research: question → literature → hypothesis
            → experiment → analysis → writeup
publishing  Publishing: idea → outline → draft → edit → publish
            → promote
design      Graphware design lifecycle: idea → spec → design
            → build → test → release | integrate
    The shipped packs are in src/workgraph/areas. The design pack (src/workgraph/areas/design.yaml) is new: its release and integrate stages both loop back to idea, and its gap rules cover idea, spec and component. Everything in the sdlc demo is driven by src/workgraph/areas/sdlc.yaml, for example test verifies requirement, and the path rule that files under tests are tagged test.

    Graph model

    Process nodes

    stage:<area>:<id> joined by precedes
    project:<name> joined to its stages

    Knowledge nodes

    files, symbols, documents, requirements, decisions, questions, hypotheses
    carry kind, project and stages, a list such as [requirement, design]
    • Edges carry relation and a confidence: EXTRACTED, INFERRED or AMBIGUOUS.
    • Analysis and clustering run on knowledge nodes only, because stage and project hubs would skew the results.
    Stage tags are checked against the pack's vocabulary, and unknown tags are rejected. Each tag is also an in_stage edge.

    Explicit links, derived links, gaps

    # docs/requirements/... frontmatter
satisfies: [REQ-001]

# any code file
# verifies: REQ-001
    • Relation names come from the pack's flow_relations.
    • Derived: when a test file imports a code file, an INFERRED verifies edge is created.
    • Gaps: the pack's expectations ("every requirement needs a test") are run as graph queries.
    • Rules can skip trivial files (min_symbols, exclude). Broken references are reported.
    The derived verifies edge follows from the pack's rules and is not hardcoded. LLM-extracted items are skipped by gap rules unless include_llm is set.

    The build pipeline

    In src/workgraph/pipeline.py, build_workspace does the following for each project in a workspace:

    processors.run_processors   # per artifact type
  → _tag                     # stage tags
  → _resolve_refs            # cross-references
  → links.cross_project_links
  → derive_flow_edges
  → graphify build / cluster  # on knowledge nodes
    • Processors: ast, frontmatter, annotations, llm, llm_items.
    • The structural build needs no LLM. LLM processors run only with --semantic.
    File walking honours .gitignore, .graphifyignore and the ignore lists of the pack and the project. The result is written to home/out/graph.json.

    Search, show and ask

    • workgraph search "checkout test": keyword search over names, paths, summaries and the first lines of each file.
    • ask is the GraphLang recipe src/workgraph/recipes/ask/:
    keywords (model) → context (program: matches + neighbours)
  → answer citing [node id] (model)
  → verify (program: every cited id was given)
  → grounded | ungrounded | empty
    • At most 3 model calls. --max-calls sets the cap and defaults to 4.
    • The command exits non-zero unless the answer is grounded. The model never decides the status.
    An ungrounded answer is still shown, but it is marked as not to be relied on. When nothing in the graph matches, the model is not asked for an answer at all. Verify allows one repair attempt.

    Semantic search with local embeddings

    $ workgraph search "how are carts stored?" --semantic
    • Tries Ollama first (default model nomic-embed-text), then sentence-transformers.
    • If neither is available, it falls back to lexical TF-IDF and says so.
    • Both embedding backends are dd-embed adapters. Settings: WORKGRAPH_EMBED_MODEL, OLLAMA_HOST, WORKGRAPH_EMBED_DEVICE.
    • The vector cache is JSON under <home>/cache/embeddings, keyed by a content hash and safe to sync.
    Ollama keeps this local and free: ollama pull nomic-embed-text. dd-embed's own pickle cache is not used, because it is keyed by the full text.

    Memory for Claude Code

    • Session start hook: tracks the project and adds a short graph summary to the context (stages, gaps, open items, product, owner, earlier changes).
    • Session end hook: records what changed and rebuilds the graph in the background.
    • /workgraph queries the graph from inside a session.
    • workgraph import-claude backfills earlier work: projects, session metadata and memory files.
    • Install with workgraph utils claude-setup --write or the plugin in plugin/. Use one, not both.
    • The plugin is not published to a marketplace yet. To try it: claude --plugin-dir <path>/plugin.
    Work done through Claude Code flows into the same graph with no manual ingestion. Data lives in ~/workgraph, or in WORKGRAPH_HOME if that is set.

    Many domain graphs that reference each other

    GraphExample hierarchy
    Repoworkspace > project > file > symbol
    Productproduct family > product > application
    Orgcompany > division > department > group > team > person
    Processrequirement spec > solution design > build > test > release
    • Each level joins its parent through part_of. References such as org:acme/payments and process:sdlc are resolved at load time.
    • All domains merge into one in-memory graph. Unresolvable references are reported as broken.
    A repo belongs_to a product, a product is owned_by an org node and follows a process. Org and process nodes are defined once, so the same team never exists as several copies. Examples are in examples/graphs.

    JSON for machines, YAML for people

    • JSON is the canonical form, used for validation, integrity checks and graph.json.
    • YAML is for review and audit, and reviewers can add comments.
    • Converters work in both directions and do not lose graph content. Validation runs on the JSON side.

    SQLite comment store

    ✔ anchors comments by file, node ID and key path
    ✔ restores them on JSON → YAML
    ✔ keeps orphaned comments and reports them
    $ workgraph utils convert examples/graphs/org.json
    YAML comments have no JSON equivalent, so a plain conversion would lose them. Anchoring by key path instead of line number means comments survive reordering and reformatting.

    One LLM seam

    • src/workgraph/llm.py is the only code that calls a model, and every backend is a dd-llm adapter.
    • Backend resolution order:
    explicit arg → WORKGRAPH_BACKEND → project backend:
  → processor backend: in pack → default cc_cli
    • cc_cli strips ANTHROPIC_API_KEY and similar variables, so calls bill the Claude Code subscription.
    • LLM processors run only with --semantic.
    • workgraph utils show-llm shows the resolved backend, billing and readiness for each processor.
    The adapters are shared with GraphLang and SPL.py, so billing fixes belong in dd-llm. A model overload stops the LLM pass with a warning and does not fail the build.

    Moving between machines

    • The database never leaves the machine.
    • Only what cannot be rebuilt travels, as text: domain files, YAML comments and the portable workspace.
    • workgraph dump / load handle a first setup, for example by USB.
    • workgraph sync push / pull go through a private GitHub repository.
    • Exports are scanned and stop on databases, large files or anything shaped like a key.
    • The org domain, session journal and LLM cache are opt-in.
    If the GitHub CLI is logged in, sync init checks that the repository really is private. The User Guide has the details under "Moving to another machine".

    How to try it

    conda create -n graf python=3.11 pip -y
conda activate graf
python -m pip install -e ".[dev]"
workgraph utils doctor      # warns [!!] in conda base

workgraph build -c examples/workspace.yaml
workgraph gaps  -c examples/workspace.yaml
workgraph gaps --src <path-or-git-url>   # no workspace file
    • Do not skip python=3.11 pip. Without it, packages end up in the base environment.
    • The structural build needs no LLM and no API key.
    Always use python -m pip so the pip from the environment is used. Git URLs passed to --src are shallow-cloned into home/src. docs/GUIDE/TUTORIAL.md is a walk-through of about 40 minutes.

    What is not done yet

    • Early hackathon prototype.
    • Process instances (a product's status within a process template) are not built. Only templates and the follows link exist.
    • Per-domain vocabulary is still Python constants in schema.py, not YAML packs.
    • Other LLM backends (bedrock, claude, gemini, ...) are wired and readiness-checked only, not exercised.
    • The Domains tab has passed headless tests but has not been looked at in a browser.
    • The plugin is unpublished. The 0.3.0 renames (domain → area, layer → domain) are not released yet.
    The design document has a status table with how far each feature was checked. For an existing home folder, workgraph utils migrate moves it to the 0.3.0 names, and --dry-run shows what it would do.
